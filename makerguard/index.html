This is the second door into the same data. The check at the top of this page tests a stranger with no login. This one tests a signed-in user reaching for rows that are not theirs.

No test user yet? This takes about two minutes, and no inbox is needed: create both users in your Supabase, under Authentication, Users, Add user, with Auto Confirm ticked. Made-up emails are fine, like test-a@myapp.com.

How do you want to sign in as A? Pick one.

The fake test account you created for testing, in your own product. Never a real customer's email.

Only if you already have a token for a test user from your own tools and prefer pasting it instead of signing in. You do not need both options. Never a real customer's token.

B

Test user B, never signs in

Create B the same way as A. Then, in Table Editor, add one fake row owned by B in your table and note the number in its id column. That number is all this check needs from B. The check signs in as A and tries to read that one row.

The number in the id column of the fake row that belongs to test user B, from Table Editor. Not A's number: A can always read A's own row, so aiming at A's row shows an Issue on every table, even a protected one. For one table, just that number. For several tables, give the numbers in the same order as your table names at the top, separated by commas. Each number is that table's own fact, nothing to do with the others, and in a fresh test setup it is often the same number every time, like 2, 2, 2. Leave a gap for a table you want to skip, like 2, , 2. Test rows only, never a real customer's row.

What you are probably wondering


Supabase already warns me about unprotected tables. Why do I need this?

The advisor reads your database settings. It never visits your live app, never tries a request as a stranger, and never signs in as one user to reach for another user’s data, which is where the worst leaks live. It also cannot see your shipped website code, where a master key would sit. This performs those tests, on any live app, whichever tool built it.




Why not just ask ChatGPT?

ChatGPT, Claude and Gemini can only judge what you paste to them. They cannot send the requests, sign in as a second user, or open your files as a stranger. They give opinions. This runs the tests.




Why should I trust the results?

Every Issue in your report is a request that actually came back with data, and the evidence is printed in its details. A test that could not be performed is marked Not checked, never guessed, and a name that is not a real table comes back Not checked, not an issue. No answer is given without the attempt behind it.




Who is behind MakerGuard?

Swati, a solo founder. Ten years at Microsoft, six of them in data security. She builds MakerGuard in public, and the contact link at the bottom of this page reaches her directly.




How much does it cost?

Nothing. It is free.




Do you store my app, my key, or my results?

No. The details you type here and the results you see are not sent to MakerGuard and are not stored by MakerGuard. The tests run in your browser, talking directly to your Supabase. If you paste your app link, the link goes to the MakerGuard reader: it reads your app's public code files, sends back what it finds, and stores nothing.




Is any of my stuff used to train a model?

No. Your key and your results are never sent to MakerGuard or stored by it, so there is nothing of yours to train on.




Is this AI?

No. There is no AI in the examiner. It runs deterministic checks and reports what came back, so a run today and a run after your fix can be compared like for like.
