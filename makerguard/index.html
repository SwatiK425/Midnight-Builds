This is the second door into the same data. The check at the top of this page tests a stranger with no login. This one tests a signed-in user reaching for rows that are not theirs.

The fake test account you created for testing, in your own product. Never a real customer's email.

B

Test user B, never signs in

Create B the same way as A. Then add one fake row owned by B in your table. Only that row’s number is needed, find it in the id column in Table Editor. The check then signs in as A and tries to read B’s row.

The number in the id column of the fake row that belongs to test user B, from Table Editor. Not A's number: A can always read A's own row, so aiming at A's row shows an Issue on every table, even a protected one. For one table, just that number. For several tables, give the numbers in the same order as your table names at the top, separated by commas. Each number is that table's own fact, nothing to do with the others, and in a fresh test setup it is often the same number every time, like 2, 2, 2. Leave a gap for a table you want to skip, like 2, , 2. Test rows only, never a real customer's row.

Your app's homepage address. Its public code files get read, the same files any visitor's browser downloads, looking only for a master key pattern. A key value is never shown. Browsers sometimes block this read; then this question stays unanswered, which is not a pass.
